## ৮.১ কমেন্টের মর্মার্থ (বাংলায়)

> NAT-aware ডিফেন্স নিয়ম: একটি IP থেকে **≥3টি ভিন্ন account সফলভাবে authenticate** করলে সেটিকে shared IP ধরে blocking IP-scoped → **email-scoped** হয়ে যায়। **একাধিক valid account-এ হাত থাকা আক্রমণকারী** এই শর্তটি ইচ্ছা করেই তৈরি করে নিতে পারে (নিজের ৩টি account দিয়ে ৩বার সফল লগইন), তারপর টার্গেট email ঘুরিয়ে ঘুরিয়ে আক্রমণ করলে IP-লেভেল blocking দুর্বল হয়ে যায়।
>
> **যা চেয়েছে:**
> 1. এই success-threshold ম্যানিপুলেশনের সম্মুখীন কিনা — মূল্যায়ন করুন
> 2. **shared-IP স্ট্যাটাস কত দিন থাকে** (persistence)
> 3. আক্রমণকারী-নিয়ন্ত্রিত account churn-এর নিচে আচরণ
> 4. Residential / enterprise-NAT / proxy পরিস্থিতিতে **security–availability trade-off সংখ্যায়** দিন

---

## ৮.২ প্রজেক্টের এখনকার অবস্থা

| বিষয় | স্ট্যাটাস |
|---|---|
| NAT-aware blocking (M9) | ✅ আছে — `success:emails:ip:{ip}` distinct-set; `SCARD ≥ MCP_SHARED_IP_SUCCESS_THRESHOLD (3)` হলে block হয় `blocked:email:{email}`-এ |
| Trade-off স্বীকৃত | ✅ THREAT_MODEL-এ লেখা: "NAT attacker can rotate accounts; accepted because IP-blocking harms legitimate users" — কিন্তু **মাপা হয়নি**, শুধু স্বীকার করা |
| Attack scenario (৩ valid account দিয়ে gaming) | ❌ নেই — `nat_shared` সিনারিওতে সফল legitimate user + আক্রমণকারী মিশ্রিত, কিন্তু **ইচ্ছাকৃত gaming** নেই |
| Shared-IP status persistence | ⚠️ সেট-এর TTL = window (900s), নতুন success-এ refresh হয় — কোড থেকে অনুমানযোগ্য, কিন্তু **মাপা/ডকুমেন্টেড নয়** |

**প্রত্যাশিত ফল:** gaming আক্রমণকারীর বিরুদ্ধে IP-block আর হবে না (email-scoped হবে), তাই email রোটেট করলে প্রতিটি নতুন email-এ নতুন করে counter শুরু — detection মূলত AI escalation + challenge-এর উপর নির্ভর করবে। এই চিত্রটাই মাপতে হবে।

## ৮.৩ কী কী করতে হবে

### এক্সপেরিমেন্ট (হার্নেসে নতুন সিনারিও)
1. **`nat_gaming` সিনারিও** যোগ করুন:
   ```
   ফেজ ১ (seeding): আক্রমণকারীর ৩টি নিজস্ব valid account দিয়ে একই IP থেকে সফল লগইন
                     → success:emails:ip সেটে ৩টি entry → IP এখন "shared"
   ফেজ ২ (attack): একই IP থেকে ২০+ ভুক্তভোগী email-এ password guessing
   ```
   মাপুন: (a) ব্লক কি email-scoped হলো (IP নয়)? (b) প্রতি নতুন email-এ detection-এ কত সময়/কত event লাগল? (c) honest/adversarial উভয় মোডে recall
2. **Persistence মাপুন:** শেষ সফল লগইনের পর shared-IP স্ট্যাটাস কতক্ষণ টেকে (TTL মান যাচাই — প্রতি success-এ refresh হয় কি না কোড দেখে নিশ্চিত করুন) — ছোট একটি টাইমলাইন টেস্ট/টেবিল
3. **Account churn:** আক্রমণকারী প্রতি N মিনিটে নতুন valid account যোগ করলে (যেমন leaked credential দিয়ে) কী ঘটে — একই সিনারিওর ভ্যারিয়েন্ট
4. **Trade-off টেবিল (পেপারে):**
   | পরিস্থিতি | Legit user/IP | আক্রমণকারী সক্ষমতা | Blocking scope | Collateral |
   |---|---|---|---|---|
   | Residential | 1–2 | একক IP | IP-scoped (পুরো) | নগণ্য |
   | Enterprise NAT | ১০০+ | এক IP + ৩ valid acct | email-scoped | 0 (সহকর্মী নিরাপদ) |
   | Proxy/VPN pool | 0 legit | অনেক IP | IP-scoped প্রতিটিতে | 0 |

### ঐচ্ছিক কোড হার্ডেনিং (একটি হলেই চমৎকার)
5. **Recency শর্ত কড়া করুন:** shared-IP সেটের entry-গুলো বর্তমান window-এর মধ্যে *সাম্প্রতিক* success থেকে এসেছে কি না যাচাই (TTL রিফ্রেশ নীতি পরীক্ষা করুন — পুরনো success যেন চিরকাল shared না রাখে)
6. এবং/অথবা **shared IP-তেও velocity গার্ড:** email-scoped block-এর পাশাপাশি ঐ IP-এর মোট failure-ভিত্তিক challenge rate-limit (per-IP challenge issuance limit আগে থেকেই আছে — `MCP_CHALLENGE_MAX_PER_IP` — এটাই এই প্রতিরক্ষার অংশ, পেপারে জোর দিন)

### ম্যানুস্ক্রিপ্ট
7. Section 4.4-এ ম্যানিপুলেশন-মূল্যায়নের ফল যোগ; Section 6/7-এ trade-off টেবিল + residual risk; Limitations-এ account-churn exposure
