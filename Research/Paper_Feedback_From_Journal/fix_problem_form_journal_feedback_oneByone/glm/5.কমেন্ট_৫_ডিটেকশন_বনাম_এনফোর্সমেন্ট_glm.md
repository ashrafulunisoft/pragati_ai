## ৫.১ কমেন্টের মর্মার্থ (বাংলায়)

> মূল্যায়ন **সমাধান-না-হওয়া HTTP 428 challenge-কে 'denied' malicious event হিসেবে গণনা করে** এবং TP মোটে জোড়ে। Challenge দিয়ে আক্রমণ আটকানো অপারেশনালি কাজের কথা, কিন্তু এর মানে এই নয় যে **classifier সঠিকভাবে malicious আচরণ চিনেছে**। ডিটেকশন/ক্লাসিফিকেশন পারফরম্যান্স এনফোর্সমেন্ট ফলাফল থেকে আলাদা করে রিপোর্ট করুন। এছাড়া **0% FPR মাত্র ৪৯টি legitimate negative-এর উপর ভিত্তি করা** — এর অনিশ্চয়তা এবং challenge-এর সম্মুখীন legitimate user-দের প্রতি সংবেদনশীলতা জোর দিয়ে বলুন।
>
> **যা চেয়েছে:**
> 1. আলাদা রিপোর্ট: explicit blocks, throttles, challenges, challenge completions, এবং **successful unauthorized attempts**
> 2. 49-negative FPR-এর অনিশ্চয়তা স্বীকার করা

## ৫.২ প্রজেক্টের এখনকার অবস্থা

| বিষয় | স্ট্যাটাস |
|---|---|
| হার্নেসে denial-এর সংজ্ঞা | ⚠️ `predictedAttack = in_array(status, [403, 429, 428])` — 428-unsolved-ও denial; অর্থাৎ **classification আর enforcement এক ঝুড়িতে** — রিভিউয়ারের অভিযোগ যথার্থ |
| Per-event outcome লগ | ⚠️ event-এ স্ট্যাটাস কোড জমা হয়, কিন্তু decision (MALICIOUS/SUSPICIOUS/SAFE) আর enforcement আলাদা কলামে রিপোর্ট হয় না |
| `Challenged` মেট্রিক | ✅ আছে (adversarial মোডে দেখানো হয়) — কিন্তু challenge-completion ও successful-unauthorized আলাদা করে নেই |
| FPR-এর CI | ❌ নেই — "FP 0/49" সরাসরি বলা হয়েছে |

**পরিসংখ্যান সহায়তা:** 0 false positive in 49 negatives → 95% CI (rule of three) ঊর্ধ্বসীমা ≈ **3/49 ≈ 6.1%**। অর্থাৎ "0%" আসলে "0% (95% CI: 0–6.1%)" — এই সৎ রূপটাই পেপারে দিন।

## ৫.৩ কী কী করতে হবে

### হার্নেস (`SecurityEvaluateCommand.php`)
1. **প্রতি event-এ দুটি আলাদা রেকর্ড** রাখুন:
   - `classification`: middleware-এর decision — MALICIOUS / SUSPICIOUS / SAFE (428-এর ক্ষেত্রে: SUSPICIOUS/captcha|otp)
   - `enforcement`: HTTP outcome — BLOCKED(403) / THROTTLED(429) / CHALLENGED(428) / ALLOWED(200)
2. **দুটি আলাদা confusion matrix রিপোর্ট:**
   - (a) *Classification*: `decision ∈ {MALICIOUS, SUSPICIOUS}` বনাম ground truth (SUSPICIOUS-কে ধরার নীতি স্পষ্ট লিখুন — বা MALICIOUS-only এক ভার্সনও দিন)
   - (b) *Enforcement*: `status ∈ {403, 429, 428}` বনাম ground truth (আগের সংখ্যা — এখন স্পষ্টভাবে "enforcement denial" লেবেলে)
3. **নতুন ব্রেকডাউন কাউন্টার:** attack event-দের মধ্যে — কতটা blocked / throttled / challenged-unsolved / challenge-completed / **allowed-through (successful unauthorized attempt)**
   - "successful unauthorized" মাপতে: challenge solve-কৃত scripted attacker simulate করুন (একবার solve করে ঢুকে যায়) — এটাই enforcement-এর আসল ফাঁক
4. **লেজিটিমেট পাশে:** কতজন legitimate user challenge-এর মুখে পড়ল (`LegitChallenged` আছে) + তারা solve করতে পারে কি না — একটি "legitimate + challenge-solve" সিনারিও যোগ করুন (মানব-মত solver)
5. সব রেটের সাথে **95% Wilson/Clopper-Pearson CI** রিপোর্টে যোগ করুন

### ম্যানুস্ক্রিপ্ট
6. Section 5.4 রিরাইট: "We report classification performance (the decision layer) separately from enforcement outcomes (the action layer)"
7. Table 6 ভাগ করুন: Table 6a (classification) + Table 6b (enforcement breakdown)
8. FPR বাক্য: "FPR = 0% (0/49; 95% CI 0–6.1%) — the negative set is small; we therefore avoid generalising production FPR from it"
9. Appendix A-তে সংজ্ঞা-টেবিল: কোন event কোন বিন্দুতে কোন ক্যাটাগরিতে পড়ে

## ৫.৫ রেসপন্স লেটারে যা লিখবেন (ইংরেজি ড্রাফট)

> **Comment 5:** We agree that enforcement and detection are different claims. The evaluation harness now records, for every event, both the decision-layer outcome (MALICIOUS/SUSPICIOUS/SAFE) and the enforcement outcome (403 block, 429 throttle, 428 challenge, challenge completion, or pass-through). Section 5.4 now reports two confusion matrices: Table 6a classifies by decision, and Table 6b reports the enforcement breakdown for attack events (blocked / throttled / challenged-unsolved / challenged-and-solved / allowed-through). We additionally simulate a challenge-solving adversary to measure successful unauthorized attempts. Regarding the false-positive rate, we now report 0/49 with a 95% confidence interval of 0–6.1% and explicitly state that the negative sample does not support production-scale FPR generalisation; sensitivity to legitimate users encountering challenges is discussed (LegitChallenged = 0 in all modes, with a challenge-solving legitimate scenario added).
